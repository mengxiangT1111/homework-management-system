# AI 批改与查重升级方案

> 分析对象：信衡平台两大核心子系统——AI 批改（Node.js + LLM）与拓扑查重（Node.js + Python FastAPI）。
> 性质：只做分析与方案设计，不改代码。文中所引用行号/文件以 2026-09 当前 main 分支为准。
> 与《大创项目申报与结题全景分析报告》R1-R8 / D1-D8 迭代计划的关系：本方案是其技术深化版，条目编号（A*/P*）与其中的 R/D 编号做了映射，可直接拆任务执行。

## 一、现状盘点

### 1.1 AI 批改：已建成的能力

当前链路（批量批改主线）：

```
教师选模板+参考答案 → POST /api/grading/tasks/batch
  → MySQL 命名锁防重 → 逐提交建 grading_tasks（模板快照固化）
  → 队列 worker（SKIP LOCKED 抢占，并发3，退避重试，僵死回收，心跳续租）
    → txt/docx 提取作答（30k字截断）
    → 提示词版本路由（稳定版/灰度版，确定性 task.id%100）
    → LLM（OpenAI 兼容，主备熔断降级，指数退避，JSON mode）
    → 三重兜底解析 → 维度对齐/钳制 → 服务端权威算分
    → 启发式置信度 → 分流：高置信自动回写 + 通知学生 / 低置信进人工复核工单
```

值得保留的资产（升级时不推倒重来）：

| 资产 | 位置 | 说明 |
|---|---|---|
| 评分模板三层结构（维度/权重/Rubric档位/扣分规则） | `src/models/grading.js` | 快照固化到任务，重试标准一致 |
| 提示词版本库 + 灰度路由 | `prompt.service.js` | 切换/回滚零重启，确定性灰度 |
| 队列基础设施 | `services/grading/queue.worker.js` | 单实例可靠，状态全在 MySQL |
| 结果解析与钳制 | `utils/gradingResultParser.js` | 纯函数、可单测 |
| 人工复核闭环 | `GradingReview`（approve/adjust/reject） | 未利用的金矿，见 A3 |
| 提示词注入防御 | 围栏 + 零宽转义 + system 数据隔离 + 满分强制复核 | 已实测修复（commit 0ee9d39） |
| 一致性基准脚本 | `scripts/grading-consistency.js` | MAE≤5 / Pearson≥0.85 等达标线已定义 |

另有旧版同步单份接口 `POST /api/ai/grade`（`aiGradingController.js`）与新链路并存：教师单题快速批改场景仍在用，内部自己实现了一套 fetch+重试（未接 `llmClient` 的熔断/主备）。

### 1.2 查重：已建成的能力

```
Node（任务队列 C(n,2) 上三角、双向落库、进度续租、指纹缓存命中复用）
  → POST :8000/api/detect（token 鉴权 + 路径围栏）
Python 四级流水线（图像类）：
  L1 pHash 初筛（汉明距离>20 直接跳过）
  L2 ORB 特征匹配（500特征点，比值测试）
  L3 OCR 文本 Jaccard（PaddleOCR，可选）
  L4 图结构（同构检测 + 近似 GED）→ 加权融合 → 阈值判可疑
非图像（docx）：正则剥 XML 抽文本 + 内嵌图 MD5 集合对比
```

工程侧亮点：COS 物化兼容、内容 MD5 指纹 LRU（跨任务命中）、进度可视化、可视化对比图端点（`/api/visualization/...`）已具备。

## 二、问题诊断

### 2.1 AI 批改的问题

| 级别 | 问题 | 依据 |
|---|---|---|
| **P0 功能缺口** | PDF 与图片/手写作答完全不能批改。两处提取逻辑都只支持 txt/docx（`grading.service.js:43`、`aiGradingController.js:160-167`），报错文案明确写着"图片/PDF 请手动粘贴" | 中小学/高校大量作业是拍照、扫描 PDF |
| **P1 质量证据缺失** | 置信度是启发式扣分（解析重试-0.15、钳制-0.1/次、缺维度-0.25…），从未用教师复核结果校准过；`grading_reviews` 里积累的 adjust 分数没有回流任何环节 | 复核数据是免费标注，闲置 |
| **P1 单次采样** | 每份作答只调一次 LLM（temperature 0.1），LLM 输出方差直接进入分数；临界分数（如 59/60）无一致性检查 | 无自一致性机制 |
| **P2 成本不可见** | `tokens_used` 已逐条入库，但没有任何看板；批量批改前教师不知道要花多少 | 管理员无法控预算 |
| **P2 模型单一** | 全局单一 `AI_MODEL`，议论文与数学题共用一个模型；备用模型仅用于故障降级，不用于质量选型 | `config/ai.js` |
| **P3 截断一刀切** | 30k 字符直接 `slice` 截断（`grading.service.js:155`），长报告被截尾不告知丢分影响 | |
| **P3 双轨维护** | 旧同步接口自带一套重试/超时实现，与新 `llmClient` 行为漂移 | |

### 2.2 查重的问题

| 级别 | 问题 | 依据 |
|---|---|---|
| **P0 算法缺陷** | ① 融合公式中 ORB 未归一化：`similarity.py/topology_detector.py:518` 用 `orb_match_count` 直接乘权重 0.10，匹配数上限 500 → 单通道最高可贡献 50 分，两张无关图匹配 10-20 个特征点也会白拿 1-2 分，系统性抬高相似度；`compute_orb_similarity` 明明已返回归一化的 0-100 分却只在图提取失败时才用。② 权重表声明 `node_type: 0.10` 但 `_compute_overall_score` 从未使用 → 四通道合计权重 0.9，10% 凭空丢失。③ `find_common_subgraph` 按节点 ID 交集计算，而每张图的节点 ID 都是独立生成的 `n0,n1,...`（`graph_extractor.py:146`），跨图按 ID 求交毫无对应关系，`details.common_nodes/common_edges` 是无意义指标 | 需要算法校准 |
| **P0 输入面缺口** | ① PDF 无处理分支：既不是图片也不是 docx，走"不同文件一律 10 分"兜底（`topology_detector.py:368`）——PDF 作业查重形同虚设。② 只比对每份提交的第一个文件（`plagiarism.service.js:39` 取 `files[0].file_path`），多文件提交漏检。③ OCR 在 `requirements.txt` 中默认注释掉 → 文本相似度常年为 0，五通道实际只剩四通道 | |
| **P1 文本查重太弱** | docx 文本走 TF+Jaccard（`topology_detector.py:760`），对"抄了但改写语序"无感；无语义层；docx 抽文本是正则剥 XML，噪音大。无代码作业查重 | 与 R/D 计划 D1 呼应 |
| **P1 阈值写死** | `overall_suspect=50 / 75` 全局常量，不可按课程/作业配置；无教师"误报/确认"反馈，阈值永远无法标定 | |
| **P2 无跨作业比对** | 只在单次作业内 C(n,2)；"传学长作业"（跨学期/跨班）完全查不出；文件 MD5 秒传数据（ChunkOwnership）已有却没用在这 | |
| **P2 性能天花板** | 单 worker 串行 + Python 单进程；60 人班 1770 对，首次指纹提取（OCR+图提取）是瓶颈，且指纹不持久化，重跑全部重算 | worker 并发=1 是有意为之 |
| **P3 报告导出缺失** | 查重结果只在页面看，无法导出归档/给学生处分依据（R1 已规划） | |

### 2.3 联动缺失

查重与批改两条链路互不知道对方的存在：教师在批阅列表看不到"这份提交最高相似度 78%"，AI 批改的高置信自动回写也不会因为"该对提交高度可疑"而转人工。这是花小成本就能带来的最大体验增益（R4）。

## 四、AI 批改升级方案

### A1（P0）PDF 与手写作答接入

**目标**：学生提交 PDF / 拍照作业后，批量批改任务不再因"无法提取"而失败。

**技术路线（推荐组合）**：

1. **PDF 文本层**：Node 侧引入 `pdf-parse`（或 pdfjs-dist）直接抽文本——90% 的"导出型 PDF"有文本层，零额外成本，优先走这条路。
2. **扫描 PDF / 图片 → OCR**：两个选项，二选一起步、可并存：
   - **方案甲（推荐先用）**：扩展 Python `detection_service`，新增 `POST /api/extract-text` 端点（启用已在依赖注释里的 PaddleOCR）。服务、鉴权、部署模式都是现成的，改动最小；PaddleOCR 中文印刷体识别率高。缺点是 paddlepaddle 依赖重（约 1-2GB），需要确认生产服务器内存余量。
   - **方案乙（生产后期切换）**：腾讯云 OCR API（与 COS 同厂，通用印刷体/手写体按量计费，约 1‰ 元/次量级）。免 GPU、免大依赖，手写体效果比开源方案稳。适合真实试点上量后。
3. **手写作答降级策略**：OCR 出来的文本 `confidence` 低于阈值（如 0.75）时，在批改结果中标记 `来源=OCR(置信度x)`，并把该任务的置信度统一下调一档（如 -0.1），倾向进人工复核——宁可信不过，不可错得分。

**改造点**：
- `grading.service.js` 的 `extractSubmissionText`：分支扩展为 txt/docx → PDF文本层 → OCR（OCR 结果同样做 30k 截断与围栏注入防御，注意图片 OCR 前先做与查重一致的路径物化）。
- `aiGradingController.js` 的单份批改同步补齐同一套提取（或直接调用新提取服务，为 A8 合并铺路）。
- 前端 `Review.vue` / 小程序批改页的提示文案与文件支持说明。
- 数据库无需变更；可选在 `grading_results` 增加 `answer_source` 字段（text/ocr/pdf）用于统计。

**验收标准**：印刷体 PDF 批改成功率 ≥90%；拍照印刷体作业 OCR 后批改结果与手抄文本一致；手写作业 100% 不静默出分（必带 OCR 标记，低置信进复核）。

### A2（P1）自一致性双评与分歧检测

**目标**：让"AI 这分打得稳不稳"可度量，而不是赌一次采样。

**设计**：不做无条件双评（成本 ×2），做**级联复评**：

- 第一次批改照常。若结果命中以下任一条件 → 自动追加第二次采样（不同 temperature，如 0.1 与 0.4；有备用模型配置时第二次可走备用模型）：置信度 < 0.8、总分处于及格线 ±5、任一维度分数距档位边界 < 1 分。
- 两次总分差 ≤ 5 分：取均值，正常分流；差 > 5 分：强制 `needs_review`，两次结果与差值都入库供教师参考。
- `grading_results` 增加可选 JSON 列 `samples`（[{total, dimensions, model, temperature}]），不破坏现有单结果结构。

**工作量**：2-3 人日，队列与解析层全部复用。这同时是 D2 一致性研究的数据生产器：`samples` 积累后可直接统计"同题重复批改极差"分布。

### A3（P1）置信度校准与数据飞轮（升级的核心杠杆）

**现状问题**：`evaluateConfidence` 的阈值（reviewThreshold=0.6）从未被验证过。假设 0.6-0.8 区间的复核工单里教师 95% 都点了 approve，说明阈值过严、浪费复核人力；反过来 0.8-1.0 区间自动回写的结果教师大量 adjust，说明自动回写太激进。**没有数据，这个最重要的分流开关就是在拍脑袋。**

**三步走**：

1. **回流统计**（先做）：新增管理端统计——按置信度区间（0.6-0.7-0.8-0.9-1.0）统计复核工单的 approve/adjust/reject 分布与 adjust 平均改分幅度。一个只读接口 + 一个简单图表即可，2 人日。
2. **阈值再标定**（基于数据）：定一个目标，如"自动回写的结果中教师事后调整率 ≤ 10%"，用上一步数据反推合理的 reviewThreshold 与各项扣分权重；此后每学期滚动校准一次。
3. **提示词回归门槛**（流程固化）：把复核工单中教师 confirm 过的样本导出为 `golden-set.jsonl`（`submitReview` 的 final_score 就是教师基准分），接入已有的 `scripts/grading-consistency.js`。**规则固化：新提示词版本若 MAE 或 Pearson 达标线不优于当前稳定版，不允许转正**——提示词版本管理 + 灰度路由是现成的，缺的就是这道质量门。这直接构成大创 D2（评分一致性实证研究）的实验基础设施。

**额外收益**：这一条做完，申报材料里"可信 AI 批改"就有了量化证据链（阈值如何标定、MAE 多少、样本多少），而不是一句口号。

### A4（P2）模型路由与成本治理

- **按模板/学科路由模型**：在 `prompt_routings` 或模板表加可选 `model` 字段，任务创建时快照进 `grading_tasks`（与模板快照同等处理）。议论文用长文本强模型、客观题用便宜模型。
- **用量看板**：`grading_results.tokens_used` 已入库，按教师/课程/模板/时间段聚合即可；管理端加一页"AI 消耗"，行级显示估算成本（单价配在 env）。
- **批量批改前预估**：创建任务接口返回预估 token（作答字数 × 系数）与费用提示，教师确认后才入队——现有弹窗流程中加一步。

### A5（P2）参考答案 / 评分模板 AI 草拟

- 教师贴题目 → LLM 生成参考答案草稿 + 建议的维度/权重/Rubric JSON → 走 `validateTemplateJSON` 校验后进模板编辑器让教师改。
- 模板结构与校验全部现成（`template.service.js`），只需一个生成接口 + 前端入口。这是教师侧感知最强、开发成本最低的一项（2-3 人日），建议放在真实试点前完成——教师建模板的门槛直接决定 AI 批改的采用率。

### A6（P2）批注定位（对应 D4）

提示词 v1.1.0 已强制 `evidence` 摘录原文。升级为：docx 经 mammoth 转 HTML 后对 evidence 做子串匹配高亮（PDF 文本层同理），`GradingResultCard` 与文件预览联动，点击扣分项跳到原文位置。把"AI 给了 82 分"变成"AI 在这三处扣了分"——透明度是师生信任的第一来源。

### A7（P3）长作答分题切分 / A8（P3）双轨合并

- A7：教师在模板里标注题数与大题分隔标记（或按空行启发式），逐题批改后汇总维度分；替代 30k 字符一刀切截断。
- A8：旧同步接口 `/api/ai/grade` 内部改调 `llmClient.chatCompletion`（自动获得主备/熔断/退避），删除 `aiGradingController` 里重复的 fetch/重试实现。行为兼容、半天到一天工作量，建议顺手做掉。

## 五、查重升级方案

### P1（P0）算法校准——先修准再谈升级

四项修复 + 一次标定，全部在 `topology_detector.py`：

1. **ORB 归一化**：融合公式改用 `compute_orb_similarity` 已返回的归一化分数（0-100），丢弃 `orb_match_count/100*100` 的伪归一化。`orb_match_count` 保留入库供展示。
2. **权重闭合**：`node_type` 权重要么真正参与融合（`compare_node_types` 已有实现，取类型相似度均值 × 0.10），要么从权重表删除并把其余四项归一到 1.0。
3. **同构加成收敛**：`is_isomorphic → ×1.2` 改为"同构时 graph 通道直接记 100 分"，不再整体乘系数（避免弱信号通道被连带放大）；同构判定本身受提取噪声影响，建议同时要求 `common` 结构一致性达标。
4. **删除或重写公共子图指标**：按节点 ID 求交集跨图无意义（每图 ID 独立从 n0 开始）。要么改为按"节点类型+标签"匹配的近似公共子图，要么从 `details` 移除，避免误导教师。
5. **阈值标定（一次性任务）**：构造标注集——历史作业中教师判定的抄袭对 ≥30、明确独立对 ≥30（可加入旋转/透视/改标签/局部增删的扰动样本，即 D5 的消融素材），扫 `overall_suspect` 阈值画出 P/R 曲线，把 50/75 换成有依据的值。

**工作量**：代码 2-3 人日 + 标注 0.5-1 人日。**这是整个查重升级里性价比最高的一项。**

### P2（P0）输入面扩展

1. **PDF 指纹分支**：`_compute_fingerprint` 增加 PDF 处理——文本层抽取（pdfminer.six / PyMuPDF）入库为 `doc_text`；页面渲染为位图（PyMuPDF）后走既有图像流水线（pHash/ORB/图提取）。这样"拓扑图作业导出成 PDF"的场景立即被覆盖。
2. **多文件提交**：`loadValidSubmissionEntries` 与单份查重都只取 `files[0]`。改为提交级聚合：submission 的每个文件都生成指纹，两提交的相似度 = 各文件对相似度的最大值；pair 行仍按（submission_id, compared_with_id）粒度落库（`details` 里记命中的文件名），DB 结构不变。
3. **OCR 启用策略**：requirements 里 PaddleOCR 默认注释 → 部署文档给出"图形作业课程必须启用 OCR"的强建议；或与 A1 方案甲合并实施（同一套 OCR 基础设施同时服务批改与查重）。
4. **docx 抽文本换正则为 python-docx**：只取 `w:t` 文本节点，去掉样式/属性噪音，与 Node 侧 mammoth 的行为对齐（同一文档两端抽出的文本应一致）。

### P3（P1）文本 / 代码查重新通道（对应 D1 第一步）

按 `content_type` 选择通道组合，是查重从"拓扑图专用"走向"通用作业查重"的关键一步：

- **文本通道（先做）**：docx/txt/PDF 文本 → 字符级 k-gram（如 k=13）→ Winnowing 指纹（MOSS 同款，w 窗口取最小哈希）→ 指纹交集估计相似度 + **最长公共片段提取**。与 Jaccard 相比，打乱语序不影响指纹命中，且能输出"第 X 段与对方第 Y 段相同 87 字"这种可直接给教师看的证据。
- **语义通道**：embedding 余弦相似度做改写检测（调用 LLM 网关的 embedding 接口，或本地 bge-small-zh，CPU 可跑）。与 Winnowing 互补：前者抓"原句照抄"，后者抓"意思一样但字不同"。
- **代码通道（分期做）**：tree-sitter 解析 Python/C/Java → AST → 归一化图（节点=语句/控制结构，边=依赖），**复用现有图比对内核**（同构 + 近似 GED）——这正是 D1 "统一图表示" 的落地路径，拓扑图查重的算法资产直接复用。
- **融合**：`buildResultRow` 的五通道扩展为按内容类型加权的通用融合；`plagiarism_results` 加 `content_type` 标记。

**工作量**：文本+语义 5-8 人日；代码通道 8-10 人日（建议放第三阶段）。

### P4（P1）阈值配置化 + 教师反馈闭环

- 作业级阈值配置（沿用作业/任务表加 JSON 配置或全局默认+覆盖）：`suspect 阈值`、`高度可疑阈值`、可选通道权重微调。
- 教师对每个可疑对标记 **"确认抄袭 / 疑似 / 误报"**（`plagiarism_results` 加 `teacher_verdict` 列 + 批量接口 + 前端按钮，改动很小）。
- verdict 数据回流：① 攒标注集供 P1 的周期性阈值再标定；② 联动 L1——被标"确认抄袭"的对，其 AI 批改分数强制转人工。
- 报告里显示教师结论，导出的材料才具备教务效力。

### P5（P1）报告导出 + LLM 可疑点解释（对应 R1）

- **报告导出**：`pdfkit`（后端已无此依赖需引入，或用 exceljs 出表格版）生成作业级查重报告：班级概览、可疑 Top N、每对的五通道明细、内嵌可视化对比图（Python 端 `/api/visualization` 已具备）、教师结论。含时间戳与作业信息，可直接归档。
- **LLM 证据解释**：对 is_suspicious 的对，把双方 OCR 文本的公共片段 + 图结构差异数据喂给 LLM，生成一段"为什么判可疑"的中文说明（3-5 句），存 `details.llm_explanation`。教师处理从"看数字猜原因"变成"读说明做判断"。成本极低（只在可疑对上触发，通常 <10 对/班）。

### P6（P2）指纹持久化与跨作业/历史库比对

- 新表 `plagiarism_fingerprints`（submission_file_id、content_md5、phash、doc_text、winnowing_minhash、graph_json、extracted_at、content_type），检测服务提取后回写（或 Node 侧代理写）。指纹有了"户口"，三件事顺势成立：
  1. **重跑/增量任务零重复提取**（同时就是 P7 的性能前提）；
  2. **跨作业比对**：新任务候选库 = 本作业提交 + 同课程历史学期的指纹（查询范围限定同 school，历史方结果脱敏为"历史提交#序号"，不暴露往届学生身份——隐私红线）；
  3. **MD5 直接命中**：分片上传/秒传链路里已有内容 MD5（ChunkOwnership），完全相同文件（传学长原文件）可零成本在任务创建时标红，不必等流水线。
- 学生上传即哈希入库涉及存储合规：指纹只存哈希与特征，不存原文副本（doc_text 除外，且随文件清理策略同生命周期删除）。

### P7（P2）性能工程

- 指纹持久化后，比对本身变成纯内存/轻计算，Node 侧单 worker 串行的瓶颈自动缓解；
- Python 侧指纹提取（OCR + 图提取）改为进程池并行（`concurrent.futures`，按候选分片），首次全班检测时间预计可降 3-5 倍；
- 大班场景把"源 i vs i+1..n"改为"指纹全部预提取 → 批量比对"，配合 pHash 初筛，绝大多数对在 L1 就结束；
- 可视化图生成（当前在检测内同步画）改为惰性生成：只对 is_suspicious 的对生成，按需缓存。

## 六、查重 × 批改联动（L1，对应 R4）

三个挂接点，从小到大：

1. **批阅列表相似度徽标**：`Review.vue` 列表联表 `plagiarism_results`（MAX similarity per submission），≥ 阈值显示红色徽标，点击进 `PlagiarismDetail`。一个接口 + 一列 UI。
2. **可疑提交强制复核规则**：`grading.service.js` 的分流逻辑增加一条——该提交在最近查重任务中 `is_suspicious=1` 时，即使 AI 高置信也不自动回写，`review_reasons` 写明"查重判定可疑，AI 分数需人工确认"。五行代码级别的改动，堵住"抄作业还能自动拿高分"的口子。
3. **复核页同屏**：`GradingReviews.vue` 复核工单里嵌入 AI 批改结果卡与查重对比图，教师在一个屏幕内完成"看分数 + 看证据 + 定结论"。

## 七、实施路线

```
第一阶段（约 1-1.5 月）——修准与打通，对应 R2/R4
  A1 PDF/手写接入批改 ｜ P1 查重算法校准 ｜ P2 查重输入面扩展 ｜ L1 联动
  里程碑：图形/文本/PDF 三类作业批改与查重全链路可用；相似度分数经过标注集标定

第二阶段（约 2-3 月）——质量闭环，对应 R1 + D2 启动
  A2 双评 ｜ A3 置信度校准+提示词回归门 ｜ P3 文本/语义通道 ｜ P4 阈值配置+反馈闭环 ｜ P5 报告+解释
  里程碑：自动回写调整率 ≤10% 有数据支撑；文本作业查重上线；查重报告可归档

第三阶段（约 3-6 月）——深化，对应 D1/D4/D5
  A4 模型路由 ｜ A5 模板草拟 ｜ A6 批注定位 ｜ P6 历史库 ｜ P7 性能 ｜ P3 代码通道
  里程碑：多模态查重框架成型（拓扑/文本/代码共用图内核）；批注定位上线
```

依赖关系提示：
- P1 的标注集 → 同时是 P4 反馈闭环和 D5 消融实验的输入，第一阶段就要开始攒；
- A1 与 P2 共用 OCR 基础设施，**应作为一个工程项一起做**（一次部署，两端受益）；
- P6 依赖 P3 的 Winnowing 指纹设计（minhash 字段一次到位，避免二次迁移）。

## 八、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 手写 OCR 识别率不足（PaddleOCR 手写中文约 70-85%） | 批改分数失真 | OCR 来源强制标记 + 置信度降级 + 低置信必进复核；试点期手写作业以"辅助教师"而非"自动出分"定位 |
| 查重误报伤害学生信任 | 教师不敢用、学生投诉 | 阈值标定偏保守（P 优先于 R）；is_suspicious 仅作提示、处分必须经教师 verdict 确认；报告呈现证据而非结论 |
| A2 双评推高成本 | API 费用增长 | 级联触发（仅低置信/临界分复评），预计增耗 <30%；配合 A4 的用量看板监控 |
| embedding/OCR 外部依赖不稳定 | 查重通道降级 | 全部通道设计为可选：embedding 不可用退 Winnowing，OCR 不可用退图像通道，MD5 兜底永远在 |
| 跨作业比对的隐私边界 | 数据合规 | 限同校、历史结果脱敏、指纹随文件清理策略同生命周期删除、教师专属权限不变 |
| Python 检测服务运维（paddle 依赖重） | 部署负担 | 生产上量大后再切腾讯云 OCR（方案乙）；detection_service 纳入 Compose 编排（R7 已列） |
